# Vitalis Anti-Drift Tooling Matrix

Part of the Vitalis anti-drift research sprint · Research lead: Daniel · 2026-06-03 · Research-only — no product code changed.

This is the single comparison sheet for every tool catalogued in the sprint. One row per tool, grouped by capability category. Every row maps back to the seven documented Vitalis agent-failure modes (F1–F7) and carries a real source link. Where a claim is a vendor's own marketing it is labelled **vendor claim**; where something could not be verified it is labelled **UNKNOWN**.

The seven failures this matrix exists to close (all documented as REAL and recurring in Vitalis's own doctrine — `VITALIS-BUILD-PROTOCOL.md` opens by stating agents "patched important systems from memory, built parallel logic, and made outputs safer-sounding but less useful"):

- **F1** — Agent ignored the existing protocol/product standard.
- **F2** — Agent solo-patched instead of routing to read-only specialists.
- **F3** — Agent built a parallel dosing system instead of reusing the canonical engine (`BLEND_SCHEDULES` / `selectedScheduleFor` / `blendScheduleFor` in `@vitalis/protocol-core`).
- **F4** — Agent softened specific protocol content into vague compliance language.
- **F5** — Agent claimed DONE on green tests while the visual/product standard failed.
- **F6** — Agent coded/claimed from memory instead of reading canonical sources.
- **F7** — Agent inconsistently used proper subagents/tooling.

The Vitalis stack the fit ratings are judged against: **Node/JS + React + Vite + Tailwind + Express + `@vitalis/protocol-core`** (note: `@playwright/test` is installed at the outer `luke-app` repo root, but its root config targets a *separate* app — it is **not** wired to the Vitalis product), with the existing enforcement primitives already in place — `research-doctrine.js` + the **RD1–RD4** acceptance tests, the `check-catalog-guard.cjs` prebuild gate, the plain-node `test/acceptance.js` suite (75/75), and the server-side **DRAFT → APPROVED_RESOURCE** approval gate. The bias throughout is **reuse > rebuild** and **JS-native > Python-boundary**.

## How to read this matrix (legend: maturity, fit, complexity)

**Maturity** — how production-ready the tool is, independent of whether Vitalis should adopt it:

- **production** — stable, widely used, safe to depend on today.
- **emerging** — real and usable, but young (pre-1.0, small adoption, or a recent rewrite); pin a version and monitor.
- **experimental** — research-grade, a fresh preprint pattern, or explicitly labelled alpha; treat as directional, not load-bearing.
- **ARCHIVED** — no longer maintained; do not adopt.

**Fit for Vitalis (HIGH / MED / LOW)** — my judgement of how well it fits *this* stack and *these* seven failures, biased to JS-native + reusing what already exists. Fit is separate from maturity: a tool can be fully production-ready and still be **LOW** fit because it is Python-only, OpenAI-model-tied, or redundant with something Vitalis already ships.

- **HIGH** — JS-native (or zero new dependency), directly closes a named failure, low friction. Candidate for the now-list.
- **MED** — real value but more setup, not yet load-bearing, or needs a verification step before relying on it.
- **LOW** — wrong stack (Python/SaaS-only), wrong model family, redundant, stale, or mismatched to Vitalis's dosing-drift failure modes.

Some HIGH-value items are tagged **(LATER)** in the Notes column — strong fit, but they earn their place only once an earlier dependency exists or a real friction shows up (Operational Simplicity).

**Implementation complexity** — what it costs Vitalis to wire in:

- **low** — drop-in / npm install / config file; hours, not days.
- **medium** — a real integration, a new service, or a verification spike first.
- **high** — new language runtime (Python), new DSL, or standalone infrastructure to operate.

**Cost / OSS** — licence and price. "OSS (MIT/Apache/ISC)" = open source, free to self-host. "freemium" = free tier + paid cloud. "vendor claim" beside a price = taken from the vendor's own pricing page, not independently verified.

**A note on three KB items I re-verified live (2026-06-03), which shift the labels:**

1. **Galileo `galileo-js` Context Adherence — left at UNKNOWN (conductor reconciliation, 2026-06-03).** One scout reported finding `contextAdherence` / `groundTruthAdherence` in `src/types/metrics.types.ts`, but this could **not** be independently reproduced — a direct raw-file fetch 404'd and the live SDK/README surface only `correctness` / `output_tone`. Per the no-unverified-citation rule it stays **UNKNOWN** pending a pinned-ref source check, matching the four sibling docs. Do **not** build an F6 grounding gate on it until confirmed. (Fit stays MED regardless; the recommendation is unchanged.)
2. **Playwright `toHaveScreenshot` options — VERIFIED.** The official [SnapshotAssertions docs](https://playwright.dev/docs/api/class-snapshotassertions) confirm `maxDiffPixels`, `maxDiffPixelRatio` (0–1 ratio), `threshold` (per-pixel, default 0.2), and `stylePath` all exist. Daniel's open unknown on `maxDiffPixelRatio`/`threshold` is closed.
3. **Vercel AI SDK — softened.** `Output.object()` (used with `generateText`/`streamText`) is the current structured-output API in AI SDK 6, verified on the [ai-sdk.dev docs](https://ai-sdk.dev/docs/reference/ai-sdk-core/generate-object). However the docs show **no explicit deprecation** of `generateObject`; both coexist in AI SDK 6. The KB's "REPLACED" is overstated — corrected here to "both coexist; prefer the `Output` API if adopting."

## Top pick per category

One pick per category, with the one-line reason and the failure(s) it closes. Picks are biased to JS-native and to reusing what Vitalis already ships.

- **Structured output & schema → Zod v4.** The one schema runtime that turns "agent invented its own structure" into a hard runtime error; ESM **+ CJS**, so it works in both the React app and the `.cjs` server gate. *(F3, F4, F6)* — [github.com/colinhacks/zod](https://github.com/colinhacks/zod). (Runner-up for the generation boundary: **Anthropic Structured Outputs** `output_config.format`, GA on Opus 4.8, zero new deps — [structured-outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).)

- **LLM eval & test frameworks → promptfoo.** MIT, JS-native, npx; its `trajectory:tool-used` assertion is the closest off-the-shelf match to Vitalis's worst failure — it *proves* the agent called the canonical dosing engine, not a parallel one — and drops into the existing `node test/acceptance.js` pattern. *(F1, F3, F4, F5)* — [github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo).

- **Tracing & observability → OpenLLMetry-js (on OpenTelemetry GenAI conventions).** Backend-agnostic OTel spans recording which dosing fn fired, drop-in for Node Anthropic calls, pairs with self-hosted Langfuse later; mind the import-order gotcha. **(LATER** — earns its place once runtime drift detection is needed.) *(F3, F7)* — [github.com/traceloop/openllmetry-js](https://github.com/traceloop/openllmetry-js).

- **Hallucination detection & grounding → Patronus Lynx.** Official TS SDK + self-hostable 8B open-weights; a binary post-generation grounding gate before DRAFT→APPROVED, scoring protocol text against `research-doctrine.js` content as context. **(LATER.)** *(F6, F1)* — [Lynx docs](https://docs.patronus.ai/docs/research_and_differentiators/Lynx/base). (Note: **galileo-js** is a JS-native alternative, but its `contextAdherence` metric is **UNKNOWN/unconfirmed** in the live SDK — verify against a pinned ref before relying on it — [galileo-js](https://github.com/rungalileo/galileo-js).)

- **Guardrails & runtime validation → Zod (runtime guard).** Most pragmatic guard for this stack — validate every agent-generated protocol object against canonical-engine-shaped schemas; a missing field is a softened output (F4), an invented field is a parallel structure (F3). Pair with a source lookup for F6. *(F3, F4, F5)* — [github.com/colinhacks/zod](https://github.com/colinhacks/zod).

- **CI guardrails & visual/screenshot QA → Playwright `toHaveScreenshot`.** The `@playwright/test` dependency is already present at the `luke-app` root (its config targets a separate app, not Vitalis), so the only work is a Vitalis-targeted config + baselines — a low-cost build that converts the doctrine-mandated but currently-manual §8 visual gate into a CI-blocking one. The highest-leverage net-new capability in the whole sprint. *(F5)* — [playwright.dev/docs/test-snapshots](https://playwright.dev/docs/test-snapshots). (Optional PR-gate layer: **Argos CI** — [github.com/argos-ci/argos](https://github.com/argos-ci/argos).)

- **Multi-agent orchestration & durable execution → Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`).** Already the runtime — enforce read-only specialists via `allowedTools` scoping + the 4-element subagent spec, rather than adding a new framework. Critical caveat: hooks don't fire for subagent tool calls (issue #34692), so keep enforcement at the existing `check-catalog-guard.cjs` prebuild gate. *(F1, F2, F3, F6, F7)* — [code.claude.com/docs/en/agent-sdk/overview](https://code.claude.com/docs/en/agent-sdk/overview). (Durable approval pause **(LATER)**: **LangGraph.js** `interrupt()` — [github.com/langchain-ai/langgraphjs](https://github.com/langchain-ai/langgraphjs).)

- **Source-of-truth hygiene & release governance → Knip + Changesets (paired).** Knip surfaces the orphaned parallel-dosing file an agent created that nothing imports (F3); Changesets blocks an agent silently bumping `protocol-core` without a human-declared rationale (F1/F2). Both zero-cost and monorepo-native. *(F3, F1, F2)* — [knip.dev](https://knip.dev/) · [github.com/changesets/changesets](https://github.com/changesets/changesets). (Domain-lint companion: **Spectral** on catalog JSON — [github.com/stoplightio/spectral](https://github.com/stoplightio/spectral).)
